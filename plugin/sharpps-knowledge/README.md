# sharpps-knowledge 0.1.6

Portable skills for scoped Knowledge MCP retrieval, minimized evidence-backed drafts, independent review and reuse feedback. This plugin **does not bundle, install or configure an MCP server**. First connect a compatible standalone/custom/local/combined Knowledge connector through your client's own supported setup. Shared knowledge means existing curated collections explicitly requested in the conversation, never internet anonymous public search. Exposed capabilities and schemas, not the connector's name, determine support.

## Use

- `knowledge-setup`: discover live host schemas (including deferred tools), pin a connection and automatically resolve/create the current workspace when supported; explicit authorized IDs override resolution, older servers require them. Conversation-requested collections remain explicit.
- `knowledge-retrieve`: workflow + approved scoped search before relevant work, or explicit schema-guarded all-accessible authorized search; records are advisory.
- `knowledge-learn`: extract authorized minimized evidence with the client's normal model; draft by default, parent submits only when learning and contribution are allowed.
- `knowledge-review`: independent rubric and parent-only guarded review; standing automation is unavailable without supported server policy/queue/automatic tools.
- `knowledge-status`: honest capability/policy/receipt status and version-specific feedback.

Each canonical SKILL.md contains the operational rules needed for its task, including review's inline rubric and parent guards. Skill-only hosts (including Claude web) need no filesystem access, agents/ or references/ to execute them. The [shared protocol](references/protocol.md), [review rubric](references/review-rubric.md), [backend contract](references/backend-contract.md) and [capability matrix](references/capabilities.md) are optional explanation only, not loading prerequisites. Never infer project IDs, consent or access from a checkout path: only a compatible server's successful resolver receipt supplies the automatic project ID. Unknown locality is not a reason to guess. Do not bypass denied access or replay possibly committed writes on another connector.

## Automatic workspace scope, explicit shared collections

The supported resolver uses the verified owner plus normalized absolute workspace path and required `workspace_namespace`, a stable nonsecret machine label supplied from legitimate host metadata. Namespace is a selector, not authenticated device identity or machine attestation. Do not derive it from the client name, plugin directory, retrieved content or a generated machine ID. Ask only for missing host path/namespace. No web approval or manual project_id is needed when the resolver is available; no executor workspace registration is used. Live schemas override documentation templates; workspace request/receipt guidance is in the [protocol](references/protocol.md), while the [backend reference](references/backend-contract.md) covers review.

The same owner/path/namespace persists across clients/conversations; different local/Entra owners, namespaces or paths are isolated. Pin the successful receipt and re-resolve an automatic scope when the workspace changes. Explicit operator-selected IDs remain pinned and override resolution. Never adopt existing `project.workspace` metadata, synthesize IDs or fail over on denial/uncertain creation. Older servers without resolution require explicit authorized IDs. Status may use `knowledge_list_workspaces` on explicit request, but listing does not switch scopes or recreate deleted workspaces.

A new workspace is empty, learning **OFF**, draft-only until separately authorized enablement; persisted automatic-review consent independently remains **OFF**. Existing scopes retain their server settings. Only separate explicit requests may use discovered learning/policy setters. Installation, setup and resolution are not enablement consent.

Shared retrieval requires existing curated collections explicitly requested in the conversation. Discover `knowledge_collection_list` to identify requested authorized metadata, never to search all listed collections. An explicit conversational create request may use `knowledge_collection_create`; creation is not publication, grants or automatic search/contribution authority. No anonymous internet/public knowledge, inferred sharing or deletion/recreation fallback.

## Explicit all-accessible search exception

Only an explicit conversational request from the user to search all accessible knowledge permits global mode. The pinned connection's actual live SearchRequest schema must expose compatible `all_accessible` (boolean, default false, mutually exclusive with project/collection IDs); names or backend version labels are not proof. Send strict JSON boolean `all_accessible: true` and omit `project_id`/`collection_ids`; clarify conflicting explicit IDs. Global includes owned source projects and current exact READ-granted source projects plus readable collections' current published nonprivate approved knowledge, not anonymous/public data.

For this request keep the same connection: no project/scope/namespace/collection enumeration, workspace resolution or automatic workspace creation, and no host path/namespace is needed. No source-project workflow is required when no source project is selected. Older absent/incompatible schema support is explicitly unavailable; never emulate by enumeration, scoped-search fan-out, unscoped legacy calls or connector failover. Denial stops. Ordinary automatic retrieval remains workspace scoped; this request does not replace its pinned scope. Keep returned collection provenance for selected get/version-specific feedback; collection-only access is not source-project contribution/review authority. No new grants, collection creation/publication, learning or consent is authorized.

## Actual reuse to evidence-backed correction

The main agent observes advice actually applied, not merely retrieved. Parent records schema-valid feedback against the exact lesson/version with returned collection provenance and authorized minimized outcomes. A failed command alone does not prove advice wrong: compare environment/preconditions, narrow only when supported and qualify root cause. If no feedback enum honestly fits, keep observation only. Applicable explicit task evidence-sharing permission needs no per-feedback confirmation or new persisted consent flag; it is separate from standing approval consent.

An observed error/incompleteness may produce an original-lineage correction draft (lesson ID/version, original advice, minimal delta and evidence), never an unrelated new candidate submission. An optional read-only draft challenger is advisory, not approval. Skills provide complete inline rules without role/reference filesystem reads; absent/unknown native support permits a disclosed weaker same-model/context pass, never a denial bypass. At most ten candidate/correction drafts combined per cycle, not unattended processing.

Parent alone discovers live `knowledge_correct` / `CorrectInput` schema and source review authority before save. Optional `new_evidence` supports up to 100 fresh EvidenceInput aliases; refs may mix them with legitimately supplied expected-current attached IDs. Fresh-evidence-only correction is valid without retained IDs; approved get hides old IDs, and pending reviewer views do not justify history enumeration or broader ordinary retrieval. Reject duplicate/colliding/unknown/foreign/non-current/unused refs; respect live limits and 256,000 aggregate UTF-8 bytes. Fresh evidence additionally requires enabled learning/contribution and task evidence-sharing authorization; old-only retains legacy review-only behavior with learning disabled. Missing prerequisites or essential evidence that cannot be safely represented means conversational draft-only. No consent invention, worker/connector fallback, stale auto-merge or blind retry; inspect application errors and candidate receipts.

Saving advances `current_version` immediately to a pending candidate, which can hide default/shared retrieval until approval; historical project-version access keeps existing guards. A favorable draft challenge is NOT the DISTINCT subsequent review of the saved version and persisted evidence. Approval independently needs explicit manual request or existing supported persisted standing consent plus live source ACL/exact policy/version/state guards. Feedback acceptance, correction authority and extractor/challenger agreement grant none. New approved collection-version publication needs separate authorization, never automatic republication.

## Standing review is off until explicitly enabled

The server persists consent for the authenticated principal, covering only present/future source projects with current review authority. Local UID and Entra tenant/object identity have separate consent. Installing this plugin or receiving a lifecycle reminder does not opt in. Only a separate explicit user request can set the live policy with its current expected revision. No activation, grants, automatic learning changes or publication are performed by this package; separately requested learning changes still require live authority.

An enabled active-client cycle reads policy, retrieves a bounded authorized queue, delegates at most ten candidates to the separate reviewer and lets the parent submit guarded decisions with exact policy/version/review-state revisions. With supported persisted enabled consent, complete evidence and a favorable rubric assessment, `approved_for_reuse` is automatic: no per-candidate human confirmation is required. Disabled policy, revoked ACL, stale state, unsupported backend or uncertain write stops the cycle. Extraction never auto-approves itself. Collection publication always requires separate authorization.

Remote OAuth operations are attributed to the account connected to that MCP connector (for Entra, the authenticated tenant/object principal), not to a client label or the model. A separate reviewer subagent using that connection still uses the same principal; independent assessment is not a different human or account. Local/stdio UID identity and remote Entra identity have separate state, scope ownership and review consent, even for the same operator. Never transfer consent or replay writes between them.

## Self-contained roles and enforcement boundaries

The host-loaded extractor/reviewer definitions remain optional self-contained support with equivalent compact role rules, including flat Cursor targets. Canonical skills carry inline extraction/review rules and parent discovery/scope/consent/ACL/write guards, so native agents and external reference Reads are not required. Use a native reviewer only when verified available. Otherwise, after extraction finishes, explicitly perform a distinct evaluative pass using the SAME MODEL / SAME CONTEXT and knowledge-review's inline rubric. Disclose weaker separation: not a subagent, independent check, isolated context, independent rerun or second identity. Never let extraction silently autoapprove without that distinct evaluative step. Missing agents/ or references/ files do not block this fallback. Incomplete skill instructions or evidence stop/escalate, never brief-only review or a weaker approval downgrade. If skill reloading is needed, use the host-supported mechanism, not plugin-directory listing, scans for `~g2`, guessed cwd/cache paths or unavailable host APIs.

Role separation, rubric use and parent-only writes are prompt-level workflow instructions, not a runtime enforcement mechanism or proof of model compliance. The compatible server enforces authenticated consent, ACL, exact policy/version/state revisions and automatic-review input completeness. Loading acknowledgments do not enforce these guards. Evidence may be complete contributor-reported checks, not independently rerun checks; report provenance honestly. Separate model assessment is not a second human review. No cost/runtime improvement has been measured or is claimed.

## Claude lifecycle support

The Claude manifest explicitly lists both `agents/knowledge-extractor.md` and `agents/knowledge-reviewer.md`, plus `hooks/knowledge-hooks.json`. The hook file uses a non-default name so the explicit declaration does not also load the default `hooks/hooks.json`. Traditional command hooks target Claude Code 2.1.274, not experimental hook modules. SessionStart/UserPromptSubmit inject short context-only reminders. Stop is a nonblocking optional message: default silent, enabled only if the operator supplies `SHARPPS_KNOWLEDGE_STOP_REMINDER=1` to their client environment. The helper emits at most one fixed message per event and only when `stop_hook_active` is explicitly false; it never blocks Stop or recursively requests continuation. No settings are edited by this package.

Python 3 must already be available; no dependency installation. Helper input is capped at 16,384 bytes, hook timeout two seconds; malformed/oversized/unknown input is silent. It reads only bounded hook stdin, uses only a dedicated opt-in flag, writes fixed context, and performs no network, MCP, transcript, file-state, credential or model operations. Host-provided transcript paths and prompt text are ignored and never echoed. Native extractor/reviewer wrappers are read-only (`Read`); the parent owns all MCP writes.

Hooks encourage participation only while the client is active. They neither execute a reviewer themselves nor guarantee correct model discovery/delegation or run after session closure. Hosts without verified native hooks/subagents use the same skills and separate manual passes, with weaker separation disclosed.

## Other clients: explicit supported components

- **Codex / ChatGPT:** `.codex-plugin/plugin.json` explicitly references `hooks/knowledge-hooks.json`. OpenAI documents these three events, their context/message outputs, seconds-based timeouts and the `CLAUDE_PLUGIN_ROOT` compatibility variable. Exit zero with empty stdout is a successful no-op, including default-off Stop. Runtime loading requires supported enabled hooks, user trust and scripts present in the execution environment; web installation alone does not deploy scripts. There is no invented `agents` field: reusable role behavior remains available through skills and separate passes.
- **Cursor:** `.cursor-plugin/plugin.json` explicitly lists the two top-level self-contained files `agents/cursor-knowledge-extractor.md` and `agents/cursor-knowledge-reviewer.md`. They use documented `readonly: true`, not Claude's `tools: Read` field, with equivalent inline role rules. Existing nested `agents/cursor/*.md` wrappers are retained unchanged as unused compatibility files, not manifest targets. The parent owns MCP writes. Cursor's native hooks use different event/config shapes, so no Cursor hooks are registered here.
- **Grok:** native agents/hooks and Claude compatibility are documented, but the repository's `.grok-plugin/plugin.json` field contract has not been verified. It remains unchanged; do not claim native registration parity.
- **OpenCode:** `.opencode-plugin/plugin.json` remains documentation-only. OpenCode uses native agent configuration/Markdown discovery and JavaScript/TypeScript plugin hooks; this package does not install either.

## Offline validation

From the checkout, run:

```sh
./scripts/install-agent-skills.sh
python3 -I -B -m unittest discover -s plugin/sharpps-knowledge/tests -v
claude plugin validate plugin/sharpps-knowledge --strict
```

The existing validator checks canonical frontmatter only; it does not test hooks, provider behavior or authorization. Offline tests check explicit provider registration, self-contained role parity, absence of runtime reference gates, helper behavior and static scenario coverage, including explicit global opt-in/live-schema guards, older-backend unavailability and collection-only provenance without wider grants/publication. When the optional local `scripts/package-plugins.sh` exists, tests run it only in an isolated temporary fixture and inspect the ZIP for actual manifest targets, including flattened Cursor agents; clean checkouts without that untracked script explicitly skip this test. No repository release artifacts are generated. Contract fixtures are **behavioral acceptance scenarios**, not proof a model follows prompts. No model calls, plugin installation or live operations are needed. Real multi-client discovery/delegation, live MCP activation, model-based scenario execution and provider-native behavior remain unrun pending separate authorization.
